LLM Council Verdict

Nihaw — On-Screen Mandarin Translation Overlay (Design Spec Review)

2026-07-13 · 5 advisors · Peer-reviewed · Chairman synthesized

Executive Summary

The Accessibility Service as primary text capture is the wrong approach. The council unanimously (4/5) flags that WeChat, 1688, and Alipay use Canvas/WebView/SurfaceView rendering — the Accessibility tree will return little-to-no usable Chinese text from these apps. The spec's architecture has an existential dependency on a component that hasn't been tested against the actual target apps.

Replace with screenshot-trigger → ML Kit Text Recognition → overlay. This works regardless of rendering engine, sidesteps Play Store policy risk, and simplifies permissions from 4 steps to 2. The Executor's two-day validation sprint (OCR logger on real device) must come before any UI code.

Where the Council Agrees

  • Accessibility Service will likely fail on Chinese apps. Four advisors independently flagged that WeChat, 1688, and Alipay use Canvas/WebView/SurfaceView rendering. The Accessibility tree in these apps returns little-to-no text.
  • Screenshot + OCR is the more reliable capture path. Three advisors independently recommended ML Kit Text Recognition on screenshots as the primary mechanism. It works regardless of rendering engine.
  • ML Kit zh→en quality for commerce vocabulary is unproven. Multiple advisors flagged that the 30MB on-device model handles basic phrases, not commerce vocabulary like "MOQ 500, FOB Shanghai, T/T payment."
  • The overlay has serious UX unknowns. Touch event propagation, scrolling behavior, and dismiss without losing state were all raised independently.

Where the Council Clashes

  • Screenshot+OCR vs. Accessibility as primary: The Contrarian argues OCR should be the path with accessibility as bonus. The Executor treats it as backup. The right answer depends on whether the user needs continuous reading (accessibility) or occasional captures (OCR).
  • Notification-first vs. floating bubble: The Executor makes a strong case for shipping a notification action in v1 (no overlay permission, no jank, simpler code). The spec assumes the bubble is essential. Unresolved without user testing.
  • Global platform vs. single-user tool: The Expansionist alone argues for 59 languages and Global South. Every other advisor and peer reviewer calls this premature. Solo dev: build for one user first.

Blind Spots the Council Caught

  • Google Play policy is a probable kill switch. Zero advisors mentioned it. Peer reviewers flagged unanimously: overlay + accessibility service scraping screen content for non-accessibility purposes matches Google's "Deceptive Behavior" policy verbatim. Side-loading in Ghana changes distribution calculus but removes automatic updates.
  • Google Translate already ships with "Tap to Translate" overlay. Peer reviewers punctured the premise: why install a 30MB model when Google already has overlay + cloud translation + OCR with zero setup? The answer can't be "on-device privacy" — the spec doesn't address privacy at all.
  • 30MB download on Ghanaian mobile networks. ML Kit downloads lazily on first call. If that call times out, the app is bricks. Needs testing before committing.
  • Touch event handling is undefined. Can the user scroll the app behind the overlay? What happens to taps? The spec is silent.

The Recommendation

  1. Replace Accessibility Service with screenshot→OCR as primary capture. This addresses the existential risk, works on all three target apps, and side-steps Play Store policy. No accessibility permission needed.
  2. Ship notification-first, not bubble-first. A notification with "Translate Screen" that triggers screenshot→OCR→overlay. No SYSTEM_ALERT_WINDOW in v1. No overlay compositing bugs. Add bubble in v1.1.
  3. Validate before building. The Executor's two-day validation sprint is non-negotiable: test ML Kit OCR on real screenshots of 1688, WeChat, and Alipay. Time the model download on MTN Ghana network.
  4. Don't try to out-Google Google. This app wins on integration (one tap captures, translates, overlays) — not on translation quality. The cloud premium tier is a distraction for Ghanaian mobile budgets.

The One Thing to Do First

Build an OCR logger app: Install on a real Android device, screenshot each of the three target apps (WeChat, 1688, Alipay), run ML Kit Text Recognition (TextRecognition.getClient), dump recognized text + confidence scores to logcat. If this doesn't return clean, actionable Chinese text across all three apps, the entire premise is dead. If it does, you have a validated path forward with zero architecture risk.

Full Advisor Responses

Contrarian "Accessibility Service will miss the text you actually need"

Here's the hard truth: this app has a fundamental blindness problem. The weakest link is Android's Accessibility Service on Chinese apps. WeChat chat bubbles use Canvas-based custom rendering. 1688 product pages are WebViews with virtual DOMs exposing zero accessibility nodes. Alipay payment confirmations render as images in some flows. The spec admits this with "WeChat-specific WebView support" as a future consideration — meaning v1 will simply miss the text the user actually needs.

ML Kit on-device (zh→en) is NOT Google Translate. The user is comparing their current workflow against ML Kit's stripped 30MB model, optimized for basic phrases, not commerce vocabulary. "MOQ 500, FOB Shanghai, T/T payment" — ML Kit will hallucinate or return gibberish.

The 50% dark overlay will be unusable over dense Chinese UIs. Make OCR-based capture the primary path. Push the accessibility listener to "nice bonus."

First Principles "You're building a battleship to cross a stream"

The real problem: Chinese text is on screen and the user can't read it. Copy-paste is the pain point, not "I need a beautiful overlay."

Three simpler paths you're ignoring: 1) Screenshot + OCR works with every app, no accessibility quirks. 2) Clipboard watcher + system toast — no overlay permissions, ships in days. 3) Modified keyboard — InputMethodService with translate button, zero permissions beyond keyboard.

The floating overlay + accessibility service combo introduces maximum complexity for maximum fragility. You'll spend 80% of your time handling edge cases where Chinese apps don't expose text, when a screenshot-based trigger gives 95% reliability with 20% of the code.

Expansionist "This is a universal translation platform for the Global South"

Same architecture, ML Kit supports 59 languages. Launch v2 with French, Portuguese, Arabic — Nihaw serves all of West Africa (300M+ people) reading Chinese commerce apps. The reverse is equally huge: English-speaking traders reading 1688 listings.

The "Translate Online" button leaves money on the table. Build a premium tier with cloud translation (Google Cloud Translation API, DeepL) for $4.99/mo. OCR is your unlock — product photos, labels, screenshots, scanned contracts. This should be v1.5, not a footnote.

Outsider "Four setup steps before a single translation"

This app can read everything on my screen — that's also the problem. Zero mention of a privacy model, data handling policy, or audit mechanism. That's a trust wall.

Four setup steps before a single translation: overlay permission, accessibility, 30MB model download, then start service. On Ghanaian mobile data, that 30MB download is a real pain point.

"Inline popup at original text position" sounds magical and probably is. Chinese apps don't always provide reliable bounding boxes. What does the user see when positioning fails? What happens to touch events on the overlay?

Executor "Build the accessibility logger FIRST"

Risk #1: Accessibility Service capture on Chinese apps. Build the accessibility logger first — a headless service that dumps text to logcat. Open each target app. If nothing useful comes through, the whole spec is dead.

Risk #2: ML Kit download on Ghanaian networks. Time it on a real device on MTN Ghana. If it times out, bundle model in APK.

Build order: 1) Accessibility logger (1 day), 2) ML Kit translate test (1 day), 3) Translation pipeline (2 days), 4) Notification shortcut — skip floating bubble in v1 entirely. Notification-first avoids SYSTEM_ALERT_WINDOW and overlay jank.
